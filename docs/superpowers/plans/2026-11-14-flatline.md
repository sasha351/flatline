# flatline Implementation Plan (overview)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement the part plans below task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Four MAX30102 heart-rate sensors drive a four-voice electronic band (drums, bass, lead, pad) that plays in the browser.

**Architecture:** An Arduino reads four sensors through a TCA9548A I2C mux and streams raw IR samples as CSV over USB serial. A static web page reads the serial port with the Web Serial API and runs per-channel beat detection. Everything after that travels on one in-page event bus (`web/bus.js`): the sound code turns frames into Tone.js notes, and the visuals code draws frames and notes. The two halves never import each other, so two people can build them in parallel and merge without conflicts. A simulator source stands in for the hardware during development.

**Tech Stack:** Arduino C++ (SparkFun MAX3010x library), vanilla ES modules, Tone.js 15.0.4 from the jsDelivr CDN, Web Serial API, native `EventTarget` for the bus, Node `assert` for tests.

**Spec:** `docs/superpowers/specs/2026-11-13-flatline-design.md`

> **Hardware changed (2026-11-14):** the Arduino + TCA9548A mux described here was replaced by a Raspberry Pi Zero 2 W reading each sensor on its own I2C bus (`pi/`). The CSV format is unchanged. See the README and the [design spec](../specs/2026-11-13-flatline-design.md). This plan is kept as written.

## Global Constraints

- Serial: 115200 baud, one line per tick: `ir0,ir1,ir2,ir3` (unsigned integers, `\r\n` or `\n`).
- Tick rate: 50 Hz (sensor 200 sps with 4x averaging).
- A missing sensor is reported as `0`.
- Channel order is fixed: ch0 = drums, ch1 = bass, ch2 = lead, ch3 = pad (`VOICES` in `web/bus.js`).
- TCA9548A mux at I2C address `0x70`; sensors on mux channels 0–3.
- Browser: Chrome or Edge only (Web Serial). Serve over `http://localhost` (secure context).
- No build step, no npm dependencies. Tone.js is imported from `https://cdn.jsdelivr.net/npm/tone@15.0.4/+esm`.
- Pure logic (`serial.js` parsing, `signal.js`, `bus.js`, `core.js`, `audio/mapping.js`) must not touch browser globals at import time, so Node can test it.
- Tests: `node web/test.mjs` with plain `assert`, no framework. Node 20 or newer (`CustomEvent` global).
- `web/audio/**` never imports from `web/ui/**`, and the reverse. They talk only through the bus.

## The contract: `web/bus.js` events

`emit(type, detail)` sends an event. `on(type, fn)` calls `fn(detail)` for each one. **Sticky** events also replay their last value to a subscriber that arrives late, so module load order never matters.

| Event | Emitted by | Detail | Notes |
|---|---|---|---|
| `frame` | core | `{ raws: number[4], ch: {finger, ac, beat, bpm, amp, inst}[4] }` | ~50 Hz. `ac` is the pulse waveform (beats point up). `beat` is true on one sample per pulse. `bpm` is 0 until two beats. `amp` is the pulse envelope (pressure). `inst` is the unsmoothed BPM of the latest beat, 0 until two beats. |
| `status` (sticky) | core | `'idle' \| 'running' \| 'disconnected' \| 'error: <message>'` | |
| `connect` | ui | none | Emit synchronously inside the click handler. Web Serial and `Tone.start()` both need the user gesture. |
| `simulate` | ui | none | Same rule. |
| `kit` | ui | a name from `kits` | |
| `route` | ui | `0..3` | Debugging with `?fill=sim`: the voice the real sensor plays. Sent when a circle is clicked. |
| `sensor` (sticky) | core | `0..3 \| null` | The voice the real sensor plays in `?fill=sim` mode, `null` otherwise. |
| `kits` (sticky) | audio | `string[]` | |
| `analyser` (sticky) | audio | `{ wave, fft }` | Each has `.getValue(): Float32Array`. `wave` is 256 samples in −1…1, `fft` is 64 bins in dB. UI calls only `getValue()`. |
| `note` | audio | `{ voice, ...params }` | Fired through `Tone.getDraw()` at the moment the note is heard. Drums: `{ voice: 'drums', drum, velocity }`. Others: `{ voice, notes: midi[], velocity, cutoff }`. |

Rules:
- Listeners ignore fields and values they don't know. The sound side may add fields to `note` or new drum names, and the visuals side must not break.
- Adding or changing an event: add a row here and in the `bus.js` header, and emit a stub value from the owning side, all on a `contract/*` branch (see below). The other side can then build against it immediately.
- Fields inside `note` that only add information (for example `pan`, `duration`) don't need a contract branch. Document them in the sound plan's A-task commit message.

## Branching workflow

Remote: `origin` (GitHub). PRs with `gh`.

1. **Foundation first.** `git switch -c foundation main`, do F1–F6, push, open a PR to `main`, and merge it. Nobody starts a track branch before this is merged.
2. **One branch per track, off the merged `main`:**
   ```bash
   # Teammate A
   git switch main && git pull && git switch -c sound && git push -u origin sound
   # Teammate B
   git switch main && git pull && git switch -c visuals && git push -u origin visuals
   ```
   Commit only files you own (table above). Small commits, one per finished step. Push at least once a day so your teammate can see where you are.
3. **Staying current.** When `main` moves (a contract change merged), update your branch:
   ```bash
   git fetch origin
   git rebase origin/main
   git push --force-with-lease
   ```
   Only ever force-push your own track branch. Never force-push `main`.
4. **Contract changes never happen on a track branch.** Anything in a "shared, contract branch only" file goes through its own short branch:
   ```bash
   git switch main && git pull && git switch -c contract/<what>
   # edit bus.js header + the table in this file + a stub emit on the owning side
   node web/test.mjs
   git push -u origin contract/<what>
   gh pr create --base main --title "contract: <what>"
   ```
   The *other* teammate reviews and merges it. Then both rebase (step 3). Keep these PRs tiny so they merge the same day.
5. **Previewing the other half early (optional, never pushed):**
   ```bash
   git fetch origin
   git switch -c try/preview origin/sound
   git merge origin/visuals
   cd web && python3 -m http.server 8000   # look, listen
   git switch sound   # or visuals
   git branch -D try/preview
   ```
   If this merge conflicts, someone edited a file they don't own. Fix that on the track branch, not in `try/*`.
6. **Integration** is Part I below.

## Part I: Integration (both teammates)

- [ ] **Step 1: Merge sound**

```bash
gh pr create --base main --head sound --title "Sound: kits, instruments, modes"
```
B reviews (listens to the sim run on the `sound` branch), then merge.

- [ ] **Step 2: Rebase and merge visuals**

```bash
git switch visuals && git fetch origin && git rebase origin/main && git push --force-with-lease
gh pr create --base main --head visuals --title "Visuals: UI and reactive graphics"
```
A reviews, then merge. Because the halves own different files, the rebase should have no conflicts. A conflict means an ownership slip: resolve it by keeping the owner's version.

- [ ] **Step 3: Tests**

Run: `node web/test.mjs` on `main`
Expected: `serial ok`, `signal ok`, `mapping ok`, `contract ok`, and any sections the tracks added.

- [ ] **Step 4: End-to-end check with the simulator**

```bash
cd web && python3 -m http.server 8000
```
Open http://localhost:8000 in Chrome. Click **Simulate**.
Expected:
- The real UI shows `running`, four live channels, and BPMs settling near 72/64/88/58.
- All four voices play using the final default kit.
- Every kit in the kit control switches the sound without errors or stuck notes.
- Both modes (or the one kept, see Step 6) work.
- The visuals react to `note` events in time with what you hear, and the `analyser` visual moves with the music.
- The DevTools console shows no errors.

- [ ] **Step 5: End-to-end check with hardware (when wired)**

Click **Connect sensors** and pick the Arduino port.
Expected: finger on sensor N lights panel N and starts voice N in time with the pulse; finger off silences it and the panel shows the no-finger state; unplugging USB shows the disconnected state and the sound stops. If the parts aren't wired yet, record this step as skipped.

- [ ] **Step 6: Decide and clean up**

Decide beats vs bits together by ear. If one loses, delete it from `audio.js`, the `mode` event, the mode control, and the contract table (one `contract/remove-mode` PR). Update `README.md` with how to pick a kit and anything else a first-time user needs.

- [ ] **Step 7: Commit and tidy branches**

```bash
git add README.md && git commit -m "docs: README for the finished app" && git push
git push origin --delete sound visuals
```
